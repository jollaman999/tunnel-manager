# 재기동, 계정 변경, 설정 화면 손질

2026-09-19

Settings 화면에서 할 수 있는 일을 늘린다. 서비스를 다시 띄우는 것, 아이디와 비밀번호를
바꾸는 것, 그리고 지금 화면이 잘못 말하고 있거나 아예 말하지 않는 것 몇 가지다.

## 결정 1 - 재기동은 자기 자신을 다시 실행해서 한다

화면에 재기동 버튼을 둔다. 문제는 "재기동" 이 무엇이냐다. 프로세스는 자기를 다시 띄울 수
없고, 끝내는 것까지가 자기가 할 수 있는 전부다.

### 감독자에게 맡기는 안은 절반만 맞다

끝내고 나면 다시 띄우는 것은 감독자의 몫이다. 같이 배포하는 systemd 유닛과 compose 파일은
둘 다 `always` 라 다시 띄운다. 손으로 띄운 경우는 아무도 안 띄운다.

운영자가 브라우저에서 버튼을 눌러 자기 서비스를 영영 끄게 되는 경로가 남는다.

### fork 후 자살은 배포되는 두 방식에서 실패한다

자식을 띄우고 부모가 죽으면 될 것 같지만 안 된다. 재현했다. 60초를 살아야 할 자식이
두 줄만 쓰고 죽었다.

```
child 2345648 alive at 11:10:07
child 2345648 still here 1 at 11:10:07
```

`setsid` 는 세션에서 빠져나오지만 **cgroup 에서는 못 빠져나온다.** systemd 는 유닛의 메인
프로세스가 끝나면 기본값 `KillMode=control-group` 으로 그 cgroup 에 남은 것을 전부 죽인다.
도커도 PID 1 이 끝나면 컨테이너가 끝나서 같이 간다.

**손으로 띄운 경우에만 되고 실제로 배포되는 두 방식에서는 안 되는 안**이다. 고치려던 것과
정반대다.

### 자기 자신을 다시 실행한다

`syscall.Exec` 는 프로세스를 새로 만들지 않고 **지금 프로세스의 이미지를 갈아끼운다.**
cgroup 을 떠나지 않으므로 systemd 가 죽었다고 보지 않는다. 확인했다.

```
round 1: pid=2359175
round 2: pid=2359175
NRestarts: 0
```

같은 PID 로 새 이미지가 돌고, systemd 는 아무 일도 없었던 것으로 본다. 이중 기동도 없다.

지켜야 하는 순서가 있다.

| 무엇 | 왜 |
|------|-----|
| 순서 있는 종료를 **먼저 끝낸다** | 아래 따로 |
| 로그를 **명시적으로** flush 한다 | exec 는 deferred 를 안 돌린다. `logger.Sync()` 를 직접 부른다 |
| `os.Executable()` 로 절대경로를 쓴다 | `os.Args[0]` 은 상대경로일 수 있고, 작업 디렉터리가 그 사이 바뀌었을 수 있다 |
| 인자와 환경을 그대로 넘긴다 | `-db` 를 잃으면 새 이미지가 다른 데이터베이스를 연다 |

열린 파일은 신경 쓸 것이 없다. Go 가 여는 소켓과 파일에는 `CLOEXEC` 가 붙어 있어 exec 에서
닫힌다.

### 포트 때문이 아니다

처음에 이 문서는 "포트를 안 놓고 exec 하면 새 이미지가 자기 포트에 못 붙는다" 고 적었다.
**틀렸다.** 리스너를 일부러 안 닫고 자기를 exec 하는 최소 프로그램으로 확인했다.

```
round 1: bound the port, pid=2556975
round 2: bound the port, pid=2556975
exit=0
```

`CLOEXEC` 때문에 커널이 exec 순간 그 fd 를 닫는다. 바로 위 문단이 말하는 것과 같은 이유이고,
두 문장이 서로 모순이었다. 포트는 순서를 어겨도 풀린다.

순서를 지키는 진짜 이유는 셋이다.

| 무엇 | 안 지키면 |
|------|-----------|
| 처리 중인 요청 | 답을 받기 전에 연결이 끊긴다 |
| **원격 호스트의 터널** | SSH 상대편에 포워딩 리스너가 남는다. 새 이미지가 같은 포트를 다시 열려다 상대편에서 거부당한다 |
| 로그 | exec 는 deferred 를 안 돌리므로 마지막 줄이 사라진다 |

가운데가 이 프로그램에 고유한 것이다. 포트는 이쪽 기계의 것이라 커널이 알아서 치우지만,
원격 호스트에 열어 둔 것은 이 프로세스가 끊어 주지 않으면 상대편이 붙들고 있는다.

### 윈도우에는 exec 가 없다

`syscall.Exec` 는 유닉스 호출이다. 윈도우 빌드에는 없으므로 빌드 태그로 가른다. 윈도우에서는
끝내기만 하고, 다시 띄우는 것은 감독자 몫으로 남는다.

**그 사실을 누르기 전에 화면이 말한다.** 서버가 자기가 어느 쪽인지 알고 있으므로 그것을
응답에 실어 보내고, 화면은 감독자에게 맡기는 쪽일 때만 안내를 띄운다. 어느 쪽인지 모르는 채
"안 돌아올 수도 있습니다" 를 항상 띄우면, 돌아오는 경우까지 겁주는 문구가 되어 아무도 안 읽게
된다.

## 결정 2 - 자격증명이 바뀌면 이 세션 말고 전부 끊는다

아이디와 비밀번호를 Settings 화면에서 바꾼다. 둘 다 **현재 비밀번호를 요구한다.** 이 저장소는
같은 이유로 setup 을 두 번 못 돌게 막아 두었다: 세션을 쥔 사람이 자격증명을 갈아치우게 된다.

### 아이디만 바꿀 때도 끊는다

처음에는 아이디는 안 끊어도 된다고 봤다. 세션은 계정 ID 로 묶여 있고 이름은 로그인할 때
비교하는 값일 뿐이라, 이름이 바뀌어도 세션은 가리키는 곳이 그대로다.

**그런데 그것이 정확히 문제다.** 자격증명을 바꾸는 이유의 절반은 "누가 알고 있을지도
모른다" 인데, 이름만 바꾸면 **이미 세션을 쥐고 있는 쪽은 그대로 남는다.** 비밀번호를 바꿀 때만
끊으면 목적이 반만 채워진다.

그래서 규칙을 하나로 둔다. **자격증명이 바뀌면, 그 변경을 한 세션만 남기고 전부 끊는다.**
설명할 것이 하나뿐이고 빠지는 경우가 없다.

값은 setup 과 같은 제약을 쓴다. 12바이트 이상 72바이트 이하다. 72는 bcrypt 가 그 뒤를 안 읽기
때문이고, 조용히 잘라 저장하면 로그인할 때 쓰는 값과 달라진다.

### 확인 칸은 화면에서만 본다

새 비밀번호를 두 번 받는다. setup 화면에도 같이 넣는다.

**두 칸이 같은지는 화면에서만 본다.** 서버는 같은 값을 두 번 받아도 알아낼 것이 없다. 오타를
잡는 장치지 서버가 검사할 계약이 아니다.

## 결정 3 - 재기동을 기다리는 설정은 서버가 말한다

설정을 저장했는데 다음 기동에 반영되는 항목이 있으면 화면이 그렇게 말한다. 그런데 그 말이
**저장 직후 한 번만** 나온다. 탭을 옮기거나 로그아웃했다 오면 사라진다. 재기동은 여전히
밀려 있는데 화면에는 아무 표시가 없다.

지금은 마지막 저장의 응답을 메모리 변수에 들고 있다가 한 번 그리고 버린다.

### 클라이언트에 적어두지 않는다

브라우저에 적어두면 될 것 같지만 두 가지가 걸린다.

1. **다른 브라우저에서는 안 보인다.** 밀린 재기동은 이 설치의 상태지 이 브라우저의 상태가 아니다
2. **지우는 일이 따로 생긴다.** 재기동이 끝나면 없어져야 하는데, 적어둔 것은 저절로 안 없어진다

### 서버가 비교해서 답한다

프로세스는 기동할 때 읽은 설정을 들고 있다. 저장된 설정과 그것을 비교하면 "지금 도는 값과
저장된 값이 다른 항목" 이 나온다. 그것을 설정 조회 응답에 같이 싣는다.

언제 들어와도, 누가 들어와도 같은 것을 본다. 재기동하면 둘이 같아지므로 **저절로 사라진다.**

## 결정 4 - `-reset-settings` 가 무엇을 안 지우는지 적는다

`-reset-settings` 는 설정을 기본값으로 되돌린다. 지금 문서와 화면이 "모든 설정이 기본값으로
돌아간다" 까지만 말한다. 읽는 사람이 궁금한 것은 그 다음이다. **호스트와 계정도 날아가나?**

안 날아간다. 같은 데이터베이스에 넣고 돌려서 확인했다.

```
BEFORE  hosts: 1 | sps: 1 | user: 1 | certs: 1 | settings: (12345, 'debug')
AFTER   hosts: 1 | sps: 1 | user: 1 | certs: 1 | settings: (8888, 'info')
```

설정 테이블만 저장한다. 호스트, 서비스 포트, 계정, 인증서는 건드리지 않는다.

**안 지운다는 말을 적는다.** 서버가 안 뜰 때 쓰는 명령인데, 쓰면 등록한 것이 다 날아갈지도
모른다고 읽히면 못 쓴다. 못 쓰면 그 명령이 있는 이유가 없어진다.

적을 곳은 다섯이다. 플래그 설명, 영문 README 두 곳, 한글 README 두 곳, 그리고 화면의 구조 카드.

## 결정 5 - 화면 손질 셋

### 파란 버튼은 속성 선택자가 만든다

파란 버튼은 `button[type="submit"]` 이 만든다. 속성 선택자라서, 버튼을 만드는 헬퍼가 내는
`type="button"` 짜리는 아무리 주된 동작이어도 그 색을 못 받는다. HTTPS 구획의 Save 하나가
그래서 혼자 흰색이다.

헬퍼는 이미 변종 이름을 받는다. 색을 클래스로도 낼 수 있게 하고 그 이름을 넘긴다.
선택자를 고치지 않는 이유는, 제출 버튼들이 지금 그 선택자로 색을 받고 있어서 건드리면 전부
따라 움직이기 때문이다.

같은 화면의 다른 흰 버튼은 그대로 둔다. 각 카드의 주된 동작이 아니다.

### 붙어 있으면 한 덩어리로 보인다

HTTPS 의 Save 와 그 아래 인증서 표가 붙어 있어 한 덩어리로 읽힌다. Save 가 인증서까지
저장하는 것처럼 보인다. 사이를 벌린다.

### 제목과 탭을 다른 줄로 나눈다

제품 이름과 탭이 한 줄에 있다. 두 줄로 나눈다. 이름은 어느 화면인지와 무관하고, 탭은
어느 화면인지를 고르는 것이라 하는 일이 다르다.

## 안 하는 것

- 계정을 여러 개로 만들지 않는다. 지금도 앞으로도 하나다
- 재기동에 비밀번호를 다시 묻지 않는다. 돌아오는 동작이다. 계정 변경은 받는다
- 감독자가 없다고 재기동을 거부하지 않는다. 없다는 것을 신뢰성 있게 판정할 방법이 없다
- 제출 버튼의 색 선택자를 클래스로 옮기지 않는다
- 지난 릴리즈 노트는 고치지 않는다
